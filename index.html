What TabShark does

TabShark opens network capture files (.pcap and .pcapng) and shows what is inside: every packet, its protocol layers and fields, and the raw bytes. It runs entirely in your browser, so nothing is uploaded.

  • Decodes Ethernet, ARP, IPv4, IPv6, TCP, UDP, ICMP, DNS, HTTP and TLS
  • Filters and searches packets by protocol, address, port, flag or text
  • Highlights the exact bytes behind any field, and the field behind any byte
  • Flags TCP resets, retransmissions, DNS errors and wrong checksums

How to use

  1. Open a capture. Drag a .pcap or .pcapng file onto the page, or press Open capture. To try it first, press Load Sample Capture.
  2. Pick a packet in the packet list.
  3. Read its layers in the protocol tree. Expand Ethernet, IP, TCP and the rest.
  4. Click a field to highlight its bytes in the hex pane. Click a byte to jump to its field.
  5. Filter with the bar at the top or the chips, for example tcp.port == 80.

Detailed guide

Open any section for a full explanation.

1. What is a capture file?

A .pcap or .pcapng file is a recording of network traffic, made by tools such as tcpdump or Wireshark. It is a list of packets. A packet is a small chunk of data sent between two devices: a web request, a DNS lookup, a ping.

Each packet is raw bytes. TabShark reads those bytes and turns them into fields you can read: who sent the packet, who received it, which protocol it used and what it carried.

2. The screen

After you open a file the page has three panes and a status bar:

  • Packet list (top): one row per packet.
  • Protocol tree (bottom left): the layers and fields of the selected packet.
  • Hex and ASCII (bottom right): the raw bytes of the selected packet.
  • Status bar (bottom): packets in the file, packets shown after filtering, the selected frame, and the field you are pointing at.

Drag the thin bars between panes to resize them. The filter bar and Find box sit above the panes.

3. Reading the packet list
  • No. The packet number in the file.
  • Time Seconds since the first packet.
  • Source / Destination IP addresses. For packets without IP, such as ARP, these show MAC addresses, and Broadcast when sent to everyone.
  • Protocol The highest layer TabShark could decode, for example TCP, DNS, HTTP or TLSv1.3.
  • Length Size of the packet on the wire, in bytes.
  • Info A one-line summary, such as a DNS question, an HTTP request line or the TCP flags.

Rows are tinted by protocol family (TCP, UDP, web, DNS, ICMP and ARP). Rows with a problem are tinted red and show a warning triangle. Use the arrow keys, PageUp, PageDown, Home and End to move through the list.

4. Reading the protocol tree

Select a packet and the tree lists its layers from the outside in:

  • Frame capture details: arrival time, length, and which protocols are present.
  • Ethernet source and destination MAC address.
  • IPv4 / IPv6 addresses, time to live, header checksum.
  • TCP / UDP ports. For TCP also the flags (SYN, ACK, FIN, RST, PSH, URG), sequence and acknowledgment numbers, window size and options.
  • Application DNS names and answers, HTTP request line and headers, or the TLS handshake with the server name.

Click the arrow to expand a layer, or use Expand all and Collapse all. TCP sequence numbers are shown relative, starting at 0, with the raw value below. Checksums are marked correct or incorrect.

5. Reading the hex and ASCII pane

Each row shows an offset, 16 bytes in hexadecimal, and the same bytes as text on the right. Bytes that are not printable characters appear as dots.

  • Click a field in the tree and its exact bytes light up in both columns.
  • Click a byte and the tree jumps to the field that owns it.
  • Hover a byte to see its offset and field name in the status bar.
6. Filtering and finding

Type in the filter bar and the list keeps only matching packets. A red outline and message explain any mistake. The chips are one-click filters; press one again to clear it.

  • tcp, udp, dns, http, tls, icmp, arp: by protocol
  • ip.addr == 192.168.1.10: to or from an address
  • tcp.port == 80, port == 53: by port
  • tcp.flags.syn && !tcp.flags.ack: connection attempts
  • frame.len > 200: larger packets
  • error: only problem packets

Combine with &&, ||, ! and parentheses. The Find box is different: it searches the text of the packets currently shown, including payload text. Press Enter for the next match and Shift+Enter for the previous one. Press / to jump to the filter bar.

7. What counts as a problem
  • TCP reset (RST) The connection was refused or aborted.
  • Retransmission The same data was sent again, usually because an acknowledgment never arrived.
  • DNS error A reply such as No such name or Server failure.
  • ICMP unreachable or time exceeded A router or host reported it could not deliver a packet.
  • Malformed packet The packet is shorter than its protocol requires.
  • Incorrect checksum Shown in the tree. Captures taken on the sending machine often show this because the network card fills in the checksum later, so it is not always a real fault.
8. Try it with the sample capture

Press Load Sample Capture, then follow these steps:

  1. Press the DNS chip. You see a query for example.com and its answer, and later a failed lookup for a name that does not exist.
  2. Clear the filter, select packet 5 (a TCP SYN). Expand the TCP layer and click Flags. Two bytes light up in the hex pane.
  3. Press the Errors chip. Three problems appear: a failed DNS lookup, a refused connection (reset) and a retransmitted TLS message.
  4. Select packet 25 (TLS Client Hello). Expand it and click Server Name to see where the website name sits in the bytes.
9. Privacy and limits
  • Everything runs in your browser. The file is never uploaded, and the page works offline.
  • TCP streams are not reassembled. A message split across several packets appears one packet at a time.
  • TLS is summarized (version, server name, cipher suites). Encrypted data is not decrypted.
  • HTTP/2, QUIC and other protocols appear as plain TCP or UDP.
